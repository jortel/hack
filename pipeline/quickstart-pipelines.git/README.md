# Quickstart Pipelines Helm Chart

A Helm chart for generating Tekton Pipelines to build and deploy Java microservices on OpenShift.

Designed as a companion generator to [quickstart-java-service](../quickstart-java-service) and [quickstart-gitops](../quickstart-gitops) in the [Konveyor](https://www.konveyor.io/) Assets Generation engine. This generator produces the CI pipeline, while `quickstart-java-service` produces deployment manifests (and a Dockerfile), and `quickstart-gitops` produces the ArgoCD configuration.

## Prerequisites

- Helm 3.x+
- OpenShift 4.x with OpenShift Pipelines operator installed

## Quick Start

```bash
helm template my-release . \
  --set application.name=my-service \
  --set application.repository.url=https://github.com/acme/my-service.git \
  --set application.assetRepository.url=https://github.com/acme/my-service-config.git
```

## What Gets Deployed

| Resource | Template | Default |
|---|---|---|
| Pipeline | `pipeline.yaml` | Always created |
| PVC (source workspace) | `pvc.yaml` | Always created |
| PVC (config workspace) | `pvc.yaml` | Created when `pipeline.updateConfigRepo` is true |

## Pipeline Flow

The default pipeline (Buildah + config repo update) runs five steps:

1. **fetch-source** — Clones the application source code
2. **fetch-config** — Clones the configuration repository (where the generated Dockerfile and deployment manifests live)
3. **prepare-build** — Copies the Dockerfile from the config repo into the source workspace (Buildah only)
4. **build-image** — Builds a container image using Buildah
5. **update-config-repo** — Commits the new image tag to the config repo, triggering ArgoCD to sync

When using S2I Java, steps 2-3 are only included if `updateConfigRepo` is enabled (S2I doesn't need a Dockerfile). When `updateConfigRepo` is disabled with S2I, only fetch-source and build-image run.

The Dockerfile is expected to live in the configuration repository, generated by the [quickstart-java-service](../quickstart-java-service) chart's `files/konveyor/Dockerfile` template.

## Configuration

### Pipeline Settings

| Parameter | Description | Default |
|---|---|---|
| `pipeline.buildStrategy` | Build strategy: `buildah` or `s2i-java` | `buildah` |
| `pipeline.dockerfilePath` | Path to the Dockerfile in the config repo (Buildah only) | `Dockerfile` |
| `pipeline.imageRegistry` | Image registry for the built image | `image-registry.openshift-image-registry.svc:5000` |
| `pipeline.imageName` | Image name (defaults to `application.name`) | `""` |
| `pipeline.pathContext` | Source context directory within the repository | `.` |
| `pipeline.tlsVerify` | Verify TLS when pushing to the registry | `"false"` |

### S2I Java Settings

Only used when `pipeline.buildStrategy` is `s2i-java`.

| Parameter | Description | Default |
|---|---|---|
| `pipeline.s2i.version` | S2I Java builder version | `openjdk-21-ubi9` |

### Config Repository Update

| Parameter | Description | Default |
|---|---|---|
| `pipeline.updateConfigRepo` | Update the config repo with the new image tag after build | `true` |
| `pipeline.configValuesFile` | Path to the values file in the config repo | `values.yaml` |
| `pipeline.configImageKey` | The key to update in the values file | `image.tag` |

To disable the config repo update step (pure build-only pipeline):

```yaml
pipeline:
  updateConfigRepo: false
```

### Workspace Storage

| Parameter | Description | Default |
|---|---|---|
| `workspace.storageSize` | PVC size for the source workspace | `1Gi` |
| `workspace.storageClass` | Storage class (empty uses cluster default) | `""` |

### Naming

| Parameter | Description | Default |
|---|---|---|
| `nameOverride` | Override the chart name portion of resource names | `""` |
| `fullnameOverride` | Override the full resource name entirely | `""` |

## Konveyor Integration

This chart follows the same Konveyor integration pattern as `quickstart-java-service` and `quickstart-gitops`. The generator addon passes the canonical configuration dictionary as a values file.

### Application Metadata

| Konveyor field | Usage |
|---|---|
| `application.name` | Pipeline resource name, image name |
| `application.owner` | `konveyor.io/owner` label |
| `application.businessService` | `konveyor.io/business-service` label |
| `application.archetypes[0]` | `konveyor.io/archetype` label |
| `application.repository.url` | Default `GIT_REPO` pipeline param |
| `application.repository.branch` | Default `GIT_REVISION` pipeline param |
| `application.assetRepository.url` | Default `CONFIG_REPO` pipeline param |
| `application.assetRepository.branch` | Default `CONFIG_BRANCH` pipeline param |

### Example Konveyor Values

```yaml
application:
  name: my-service
  owner: jsmith
  businessService: payments
  archetypes:
    - spring-boot-api
  repository:
    kind: git
    url: https://github.com/acme/my-service.git
    branch: main
  assetRepository:
    kind: git
    url: https://github.com/acme/my-service-config.git
    branch: main
    path: /
```

### Three-Generator Flow

When all three Konveyor generators are used together:

1. **quickstart-java-service** generates deployment manifests + Dockerfile → pushed to the config repository
2. **quickstart-pipelines** generates a Tekton Pipeline that builds the image and updates the config repo with the new tag
3. **quickstart-gitops** generates an ArgoCD Application that watches the config repo and deploys changes

The pipeline closes the loop: code push → pipeline builds image → pipeline updates config repo → ArgoCD detects change → deployment rolls out.

## Triggering a PipelineRun

After the pipeline is created, trigger a run:

```bash
cat <<EOF | oc create -f -
apiVersion: tekton.dev/v1
kind: PipelineRun
metadata:
  generateName: my-service-run-
spec:
  pipelineRef:
    name: my-service
  params:
    - name: NAMESPACE
      value: $(oc project -q)
  workspaces:
    - name: source
      persistentVolumeClaim:
        claimName: my-service-source
    - name: config-source
      persistentVolumeClaim:
        claimName: my-service-config
EOF
```
